Q: Which 1–2 steps in your Section 2 pipeline are the most time-consuming?

A: The two most time-consuming steps are:

   2. STEP 4: Merge Datasets (0.011s, 10% of total time)

   While Step 2 appears fastest in absolute terms, when scaled to the full 
   dataset (12 years × 4 tables × 51 states = 2,448 files), file I/O becomes 
   the dominant bottleneck. The merge operation also scales poorly with data 
   volume due to its O(n×m) complexity.

------------------------------------------------------------------------------

Q: Why can these steps be optimised using MapReduce?

A: These steps are suitable for parallel processing because:

   1. **Data Loading (Map Phase)**: Each CSV file is independent and can be 
      read in parallel. There are no dependencies between files - perfect for 
      the "embarrassingly parallel" pattern. Each mapper reads one file and 
      emits (county_fips, record) pairs.

   2. **Merge/Join (Reduce Phase)**: The merge operation groups records by 
      county FIPS code. This is a classic reduce operation where all records 
      with the same key are collected and combined. The shuffle phase 
      automatically handles the grouping.

   Key characteristics making this MapReduce-suitable:
   - Independent data partitions (files)
   - Associative and commutative aggregation operations
   - Natural key-value structure (FIPS code → county data)
   - No inter-record dependencies within the map phase

Q: Have you defined your Map and Reduce functions clearly?

A: Yes. Key-value design:

   MAP FUNCTION:
   - Input: (filename, file_contents)
   - Process: Parse CSV, extract county FIPS and year
   - Output: (county_fips, {year, economic_data, voting_data})

   ```python
   def map_function(filename, contents):
       for row in parse_csv(contents):
           county_fips = row['state_fips'] + row['county_fips']
           yield (county_fips, {
               'year': row['year'],
               'source': 'economic' if 'DP03' in filename else 'voting',
               'data': row
           })
   ```

   REDUCE FUNCTION:
   - Input: (county_fips, [list of records])
   - Process: Group by year, merge economic + voting data
   - Output: (county_fips, merged_record)

   ```python
   def reduce_function(county_fips, records):
       by_year = defaultdict(dict)
       for record in records:
           year = record['year']
           by_year[year][record['source']] = record['data']
       
       for year, data in by_year.items():
           if 'economic' in data and 'voting' in data:
               yield (county_fips, merge(data['economic'], data['voting']))
   ```

A: Implementation using PySpark Core RDD API:

   ```python
   from pyspark import SparkContext
   
   sc = SparkContext("local[*]", "ACS_Voting_Merge")
   
   # Load economic data as RDD
   economic_rdd = sc.textFile("data/acs_merged/economic/*.csv") \
       .map(parse_economic_row) \
       .map(lambda r: (r['full_fips'], ('economic', r)))
   
   # Load voting data as RDD
   voting_rdd = sc.textFile("data/countypres_2000-2024.csv") \
       .map(parse_voting_row) \
       .map(lambda r: (r['full_fips'], ('voting', r)))
   
   # Union and reduce by key
   merged_rdd = economic_rdd.union(voting_rdd) \
       .groupByKey() \
       .mapValues(merge_records) \
       .filter(lambda x: x[1] is not None)
   
   # Aggregate by winning party
   result = merged_rdd \
       .map(lambda x: (x[1]['winning_party'], x[1]['population'])) \
       .reduceByKey(lambda a, b: a + b)
   
   result.saveAsTextFile("output/party_population")
   ```

PROBLEM (MAIN BOTTLENECK)
================================================================================

Q: What is the main difficulty in your MapReduce implementation right now?

A: **Data Skew in County Population Distribution**

   The primary bottleneck is data skew during the reduce phase. Democratic-
   winning counties (546) have 7× larger average populations than Republican-
   winning counties (2,569). This means:
   
   - Reducers handling Democratic counties process more voting records
   - Uneven partition sizes cause some reducers to take much longer
   - The slowest reducer determines overall job completion time
   
   Mitigation strategies being considered:
   1. Salted keys to distribute large counties across multiple reducers
   2. Combiner functions to pre-aggregate before shuffle
   3. Custom partitioner based on expected record counts

MAPREDUCE SOLUTION DETAILS
================================================================================

STEP 1: Map Phase - Data Loading and Key Assignment
---------------------------------------------------
Each input file is processed independently. The mapper extracts the county 
FIPS code as the key and emits the full record as the value.

```python
# Map function for economic data
def map_economic(line):
    fields = line.split(',')
    state_fips = fields[3].zfill(2)
    county_fips = fields[4].zfill(3)
    full_fips = state_fips + county_fips
    return (full_fips, ('economic', fields))

# Map function for voting data  
def map_voting(line):
    fields = line.split(',')
    county_fips = fields[2].zfill(5)
    return (county_fips, ('voting', fields))
```

STEP 2: Shuffle Phase - Automatic Grouping
------------------------------------------
Spark automatically groups all records with the same county FIPS code and 
sends them to the same reducer. This is the most network-intensive phase.

STEP 3: Reduce Phase - Merge and Aggregate
------------------------------------------
The reducer receives all records for a county and merges economic data with 
voting data, then computes the winning party.

```python
def reduce_merge(county_fips, records):
    economic_data = None
    voting_data = []
    
    for source, data in records:
        if source == 'economic':
            economic_data = data
        else:
            voting_data.append(data)
    
    if economic_data and voting_data:
        winner = max(voting_data, key=lambda x: int(x['votes']))
        return {
            'county_fips': county_fips,
            'population': economic_data['population'],
            'winning_party': winner['party']
        }
    return None
```

WHY RESULTS DEVIATE FROM EXPECTATIONS:
--------------------------------------
**Expected**: 4-8× speedup with parallel processing
**Actual**: 0.08-0.20× (5-12× SLOWER than baseline)

The deviation is explained by:

1. **JVM Startup Overhead**: Spark requires ~1-2 seconds to initialize the JVM,
   load classes, and set up the execution environment. For a job that completes
   in 0.1 seconds with Pandas, this overhead is 10-20× the actual work.

2. **Dataset Size Too Small**: Our dataset (67 MB, 97K records) is below the
   threshold where MapReduce provides benefit. The rule of thumb is:
   - < 100 MB: Use single-threaded processing
   - 100 MB - 10 GB: Consider local parallelism
   - > 10 GB: MapReduce/Spark provides clear benefit

3. **Serialization Overhead**: PySpark must serialize Python objects to JVM
   and back, adding latency for each record processed.

4. **Task Scheduling Overhead**: Creating and scheduling parallel tasks has
   fixed costs that exceed the computation time for small datasets.

WHEN MAPREDUCE WOULD PROVIDE BENEFIT:
-------------------------------------
MapReduce optimization becomes valuable when:
- Dataset size > 1 GB (our full 12-year dataset approaches this)
- Processing time > 10 seconds (amortizes startup overhead)
- Distributed cluster available (network parallelism)
- Memory constraints require distributed processing

CONCLUSION:
-----------
The MapReduce implementation is correct and functional, but the current dataset
is too small to benefit from parallel processing. The overhead of Spark's
distributed computing framework exceeds the computation time. For production
use with larger datasets (>1 GB), the MapReduce approach would provide
significant speedup, especially on a multi-node cluster.
